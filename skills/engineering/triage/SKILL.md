# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too. A PR is an issue with attached code: same roles, same states, same machine, with the deltas marked "for a PR" below. Resolve a bare `#42` to an issue or a PR per the tracker config.

Every comment or issue posted to the issue tracker during triage starts with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `.out-of-scope/` knowledge base works

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on the reporter
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs a human
- `wontfix`: will not be actioned

For a PR, the same states read against the attached code. `ready-for-agent` means a brief is attached and an agent should take the next step on the diff. `ready-for-human` means a human should merge it.

Every triaged issue carries exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names. The label strings in the issue tracker may differ. The mapping should have been provided to you. If not, tell the user to run `/setup-matt-pocock-skills`.

State transitions: an unlabeled issue normally goes to `needs-triage` first. From there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time. Flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let us look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What is ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only external PRs (the tracker config defines who counts as external), so a collaborator's in-flight PR is not triage work. This filter is discovery-only. An explicitly named PR is always triaged, whoever wrote it.

Show counts and a one-line summary per item. Let the maintainer pick.

**Done when:** the three buckets are listed oldest first, each line is tagged when PRs are in scope, and the maintainer has been asked to pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse prior triage notes so you do not re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks: (a) **redundancy**: search for an existing implementation of the requested behaviour by domain concept, not only the request's wording, and report where you looked. If found, it is an already-implemented `wontfix` (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

   **Done when:** the full thread is read, the redundancy search names where you looked, and any matching out-of-scope file is surfaced.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary (including whether it is already implemented). Wait for direction.

   **Done when:** the recommendation is stated and you are waiting, or the maintainer has answered.

3. **Verify the claim.** Before any grilling, check that the claim holds. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report what happened: confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal).

   **Done when:** the report says confirmed, failed, or insufficient detail, with the evidence.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round at a time. Domain terms sharpen, and `GLOSSARY.md` and ADRs update as decisions land.

   **Done when:** the request is specific enough for a brief, or grilling was not needed and that is stated.

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: same structure as an agent brief, noting why it cannot be delegated (judgement calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - For `wontfix`, close the issue. The comment depends on why:
     - **Already implemented**: the change already exists. Point to where it lives. Leave `.out-of-scope/` alone. That knowledge base is for rejected requests, not built ones.
     - **Rejected (bug)**: a polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role. Optional comment if there is partial progress.

   **Done when:** the role is applied, the matching comment is posted with the AI disclaimer, and a rejected enhancement has an `.out-of-scope/` file.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you are about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief.

**Done when:** the role is applied, the confirmation happened first, and a brief was written only if they asked for one.

## Needs-info template

```markdown
## Triage Notes

**What we have established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work is not lost. Questions are specific and actionable. "Please provide more info" is not a question. The positive target is a question the reporter can answer in one reply.

## Resuming a previous session

If prior triage notes exist, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Leave resolved questions closed.

**Done when:** the updated picture distinguishes answered questions from still-open ones.
